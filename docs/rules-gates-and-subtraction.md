# 规则、闸门与减法：一个长期在线 Agent 的治理复盘

> 本文是个人部署的复盘，不是产品介绍。里面所有数字都来自实际运行记录，所有失败都是真发生过的。

一个持续在线的 agent 会积累出几十条规则：外发要先问、破坏性命令要先说清、长任务要建进度卡、收尾要自查。这些规则最初都以自然语言写在指令文件里，看起来很清楚。

问题在于，规则的存在感和规则的有效性是两件事。下面六段是六次翻车，以及每次翻车之后长出来的机制。顺序不是设计出来的，是被迫的。

---

## 1. 规则写了，但不知道有没有被遵守

最早的判断方式是靠回忆：这次有没有按规矩来。单次任务里勉强可用，一旦并行几个任务就失效——注意力在人这边，不在系统这边。一个人能跟进的活跃任务有限，且不一定能完整记起定下的规范。

改成量化：把规则按执行强度分四档。

- **拦截**：不做就执行不下去
- **收尾**：不做会留下痕迹
- **检测**：事后能查出来
- **提示**：只能靠自觉

只有前两档算约束，后两档是愿望。分完档之后出现了第一个意外：**长任务建进度卡的覆盖率是 0.0**。一周内 17 个长任务，一张卡片都没有。

规则在文件里写着，实际执行是零。

这个数字的价值不在于“做得差”，而在于它让“没做到”第一次变成可观测的。在此之前，这件事既没被记录，也没被否认。

同一批数据里还有另一个数字：整体规则依从率 0.462。看上去比 0.0 好得多，但它和 0.0 讲的是同一件事——**大部分规则处在“写了但没生效”的状态**。

---

## 2. 散文条款无法被机械检查

规则写成自然语言，最大的问题不是模型看不懂，而是**没人能验证它**。

一个具体例子：长任务的判据是“工具调用次数多或耗时长”。这条规则在文件里出现一次，实现它的脚本里写了具体阈值，行为审计里又写了一遍。三处独立维护，改一处忘两处就成了常态。

真正暴露问题的方式很朴素：某次核对时发现同一个指标算出来是 0.733，换个口径算出来是 0.462。差异来源是分母——一个口径含未结束的时间窗，另一个不含。两个数都“对”，但它们不能一起用。

于是把阈值收归单一来源：所有阈值只在一个脚本顶部定义，其余地方引用它。再加一层静态检查，扫描规则文件和文档，确认里面出现的每个数值与那个单一来源逐字一致。

这层检查还顺手解决了另一个问题：**死引用**。规则里写“跑某个脚本”，但那个脚本可能早就改名或删掉了。静态检查能把“文中提到但文件不存在”的引用找出来。

但检查器本身也需要被检查。某次发现它把合法的引用误报成死引用——原因是它只按工作区根目录解析相对路径，不认“被检查文件所在目录”。误报的代价不是烦，是让人不敢用：一跑就红一片，于是只敢在单个文件上跑，等于没有覆盖。

这件事给了一个不太舒服的结论：**检查器的错误方向和它的功能一样重要**。漏报让你以为很安全，误报让你干脆不用。

## 3. 规则文件长到了 22,000 字符

上下文体检时出现一个此前没注意的数字：规则文件本身 22,151 字符。

这个体量的问题不在于“占地方”，而在于注意力分布不均匀。任务描述、工具结果、对话历史都要和它共享窗口，而模型对上下文中段的关注度并不一致。规则写得越多，越可能被无视的正是中间那些条款。

直觉做法是删掉不重要的。但一动手就遇到一个无法回答的问题：哪条不重要？没有使用数据时，这个问题无解。

先解决前提。规则按“能否机械判定”分成两类：能写成阈值判断的（例如单轮工具调用达到某个次数即视为长任务），和不能的（例如“拿不准就先问”）。前者可以交给脚本，后者只能留在文本里。

分类之后做了两件事：把实证与证据搬到独立文件，正文只留结论和指针；把可机械判定的部分转成脚本，正文只留触发条件。

结果：22,151 → 13,370 字符，降幅 39.6%。

但“变短”不等于“没丢”。这一节的重点是如何证明没删掉不该删的。

采用联合计数：统计规则文本中的条件标记（必须 / 禁止 / 当…时 / 阈值 / 判定），要求精简版与移出文件的标记总数不低于原始版。结果 268 ≥ 233。

看上去通过。但分类看，「必须」这一类是 105 vs 107，少了两个。抽查消失的 22 行中的 8 行，发现两种成因：措辞改写（同一条义务换说法），以及并入开头硬约束（原文“触发：任何外发 → 必须先问用户”变成“外发 → 先问用户，不得擅自”）。

剩余 14 行未逐条核。因此准确表述不是“没有丢失”，而是“总量未丢，但 −2 未归因”。这条存疑保留在报告里，没删。

更值得注意的是后续：一个月后规则文件回到 15,486 字符，因为新机制带来了新条款。精简不是一次性动作，而是周期性维护——不做，它就会涨回去。

## 4. 闸门存在，但没人验证闸门

有了一条规则之后，自然会想把它变成闸门：不可逆操作前必须填表、必须给回滚路径、必须确认批准。

闸门写好了。但很快遇到一个更麻烦的问题：**怎么知道闸门真的拦得住？**

做法是留基线再对照：先记录改造前的行为（哪些命令被放行、哪些被拦），然后用同一组用例跑改造后的版本，逐条比对。关键是必须包含**阴性对照**——即“本该被放行”的用例。只有“该拦的拦住了”不够，还得证明“不该拦的没被误伤”。

实测下来，一个常见的拦截层（路径包装器）只能防误触：它能拦住手滑输入的命令名，但用绝对路径调用就绕过去了。这不是实现粗糙，而是这一层的设计目标本来就有限。

所以绕过面必须写出来，而不是等别人发现。文档里明确标注：这一层只防误触，不防刻意绕过；真正的防线是执行前的人工确认和后置的绕过扫描。

这里有个反直觉的观察：**写得越诚实的防护说明，越不容易被误信**。反过来，声称“全面防护”的说明，会让人跳过那些本该保留的人工检查。

## 5. 不知道“正常”是什么样

前四段都在处理“规则有没有生效”。第五个问题是：**怎么知道系统行为变了？**

最初靠感觉：最近好像慢了点、好像老是触发压缩。这类判断无法复盘，也无法证伪。

于是开始记录。持续记录每个会话的上下文水位、每次压缩的前后值、每次触发的来源。两个月下来积累出十九次压缩事件，幅度从中位 84% 到最大 97%。

单次最极端的一次：591,669 → 23,350 token，砍掉 96%，耗时 61 秒。

这组数字改变了原本的判断。此前把压缩当成“优化”，看到分布才意识到它是**抢救**——只在快撑爆时发生，从几乎满直接砍到几乎空，中间没有渐进。真正的结论不是“压缩很有效”，而是“从来没有及时压缩过”。

记录过程本身也出过一次错。最初的水位监控用的是字节数，而引擎真实的压缩阈值是 token 数。换算下来，字节口径的红线几乎永远到不了——监控看起来很安静，实际上一直在漏报。

**测量工具用错尺子，比没有测量更危险**，因为它会给出“一切正常”的结论。

---

## 6. 结论没人能复核

前五段所有结论都是自证的：自己定的指标、自己跑的数据、自己写的判断。这在方法上不成立。

最后一个机制是把自己从复核环节里移出去：产出结论的 agent 不参与复核，另起一个独立会话，只看文件、只核事实、不改结论。

具体做法是抽查而非全查：从报告里挑 5 个核心数据点，每个都要求重新取一手证据，不接受引用原报告作为证据。然后逐点给出“报告说 X → 实测 Y → 结论（一致 / 不一致 / 无法核实）”。

最近一次复核的结果：5 个点全部一致，0 个不一致，0 个无法核实。但同时发现两处别的问题——一处引用行号不全（事实无误，引用不精确），两处 GitHub 星标与 issue 数在取证后又变了（活值漂移，不是错误）。

这次复核最值得记的不是“全部一致”，而是它暴露了复核流程自身的边界：**它只能验证被抽查的点**。5 个点全对，不等于 50 个点全对。

---

## 收束：三条可以带走的判断

**第一，结构优于提示词。** 一条规则如果反复失效，通常不是措辞问题，而是它没有变成结构。把约束从文本搬到系统里——让工具缺失、让闸门拒绝、让计数自动跑——比继续润色句子有效。

**第二，可证伪优先于完整性。** 每个检查都需要一个已知会失败的样本，先证明它能抓错，再相信它的通过。没有阴性对照的“通过”，和没有检查是一回事。

**第三，减法是最难的杠杆。** 加一条规则很便宜，看起来很有产出；删一条要求先知道它从没触发过。所以删除清单必须先建，否则规则只会单调增长。

## 适用边界

这套做法是为单人长期部署设计的，前提是：规则会长期积累、任务会并行、结论需要被信任。

不适用的情形也很明确：规则少于三十条时，治理开销大于收益；单用途、短生命周期的 agent 不会积累，也就不会漂移；团队场景则多出一层问题——谁的规则算数、变更怎么评审——本文没有覆盖。

如果只带走一句话：**规则的有效性不能靠自觉，得靠可观测的失败率。**
